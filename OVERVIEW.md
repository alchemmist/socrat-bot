# Socrat Bot — обзор проекта

Socrat Bot — Telegram control plane для домашнего кластера Socrat: интерфейс
уведомлений, пользовательских интересов и подтверждаемых действий. Проект не
заменяет Kubernetes, Grafana или систему автоматизации. Он связывает их с Telegram,
сохраняя состояние, права пользователей и результаты доставки в базе данных.

Пользовательский интерфейс бота — на английском. Этот документ описывает устройство
проекта; подробные контракты и инструкции находятся в [README](README.md),
[OpenAPI](openapi.yaml) и тематических документах в [docs](docs/).

## Что умеет бот

- Доставляет карточки алертов отдельным получателям, обновляет их при изменениях
  и закрытии инцидента, поддерживает Mute и явную эскалацию между уровнями.
- Добавляет ссылки на Grafana, Rancher, логи, Argo CD и связанные материалы;
  внешние workflow могут дополнять существующие карточки ссылкой SPI и заметкой.
- Показывает график алерта как основное фото, когда доступен проверенный снимок,
  и ссылку **Chart** на соответствующую панель и временной диапазон.
- Хранит независимые интересы **VPN**, **Alerts**, **LLM** и **Cluster**. Один пользователь
  может выбрать несколько направлений одновременно.
- Даёт владельцу создавать немедленные и отложенные рассылки по выбранной группе,
  сохраняет нативное Telegram-форматирование, историю и IDs отправленных копий
  для последующего редактирования.
- Предоставляет внутренний HTTP API для интеграций и отдельный sudo broker.
- Содержит отдельный процесс проверки и обновления панели 3X-UI.

Выбор VPN не создаёт VPN-доступ, а выбор LLM не выдаёт API-ключ. Это интересы
к функциональности и соответствующим рассылкам, а не самостоятельные полномочия.

## Архитектура

```text
                         Telegram
                      webhook │ ▲ Bot API
                              ▼ │
Внутренние workflow ──► Bot / HTTP API ──► PostgreSQL
  (например, n8n)       │      │              ▲
                       │      ├─ фоновые очереди доставки/графиков
                       │      ├─ Alertmanager: silence
                       │      └─ graph gateway ──► Grafana / renderer
                       │
socrat-sudo ──► Sudo broker ──► запрос подтверждения в Telegram
                       │
                       └─ отдельный 3X-UI updater ──► Kubernetes API
```

Это схема взаимодействий, не единая цепочка выполнения: sudo broker и updater
работают отдельными процессами, а не внутри обработчика Telegram-команды.

### Один образ, три процесса

| Процесс | Точка входа | Назначение |
| --- | --- | --- |
| Bot | `python -m socrat_bot` | FastAPI, Telegram webhook, команды, callback-кнопки и фоновые обработчики |
| Sudo broker | `python -m uvicorn socrat_bot.broker:api --host 0.0.0.0 --port 8080` | Запрос разрешения, ожидание подтверждения, фиксация результата sudo-запроса |
| 3X-UI updater | `python -m socrat_bot.updater` | Проверка версии и выполнение обновления выделенного Deployment панели |

Docker-образ по умолчанию запускает bot на порту 8080; `PORT` позволяет изменить
порт. Адреса Service, probes, RBAC, ingress и размещение процессов задаются
инфраструктурой, а не этим обзором.

### Технологии

- Python 3.12+.
- FastAPI и Uvicorn для HTTP.
- `python-telegram-bot` 21.x для Telegram; в production используется **webhook**,
  не polling.
- SQLAlchemy 2 и Alembic для данных и миграций.
- PostgreSQL в production; SQLite также используется в изолированных тестах.
- HTTPX для обращений к внешним API.
- Pytest, Ruff и Quality Graph для проверок.

## Пользователи, интересы и права

`/start` показывает **Welcome to Socrat Bot!** и **I'm interested in…**
с независимыми флажками VPN, Alerts, LLM и Cluster.

Понятия намеренно разделены:

| Понятие | Где хранится | Что означает |
| --- | --- | --- |
| Идентичность и роль | `users` | Telegram ID, username, `owner` / `user` |
| Интерес к функции | `user_interests` | Строка `(user_id, topic, enabled)` |
| Одобрение алертов | `users.alerts_approved` | Сохранённое разрешение владельца |
| Уровни алертов | `users.admin_level`, `users.receive_level` | Полномочия и глубина получения |
| Привязка VPN | `users.panel_client_id`, `link_codes` | Связь с клиентом панели; не подписка на рассылки |

Для алертов одного выбранного интереса недостаточно: также нужно одобрение.
Пока его нет, Alerts отмечен как ожидающий подтверждения, но доставка запрещена.
Выключение Alerts сохраняет одобрение; повторное включение не требует нового
подтверждения и не запускает рассылку старых инцидентов.

Роли не кодируют интересы. Историческая роль `vpn` и пользовательские столбцы
`uses_vpn` / `alerts_enabled` заменены новой моделью. Для нового интереса не нужен
ещё один boolean-столбец: нужно зарегистрировать тему и подключить её поведение.

Основные команды:

- `/start` — выбрать интересы в личном чате.
- `/alerts` — настройки получения алертов.
- `/unsubscribe` — выключить Alerts, сохранив одобрение.
- `/users` — кнопки VPN, Alerts, LLM и Cluster; по нажатию список выбравших этот интерес, только для владельца.
- `/alertlevel` — изменение admin level, только для владельца.
- `/mailing` — создание групповой рассылки, только для владельца.
- `/mailing_edit` — история доступных рассылок и редактирование отправленных копий.

Канонический реестр команд и меню — [commands.py](src/socrat_bot/commands.py).
Telegram-меню не является границей авторизации: права проверяются в обработчиках.

## Как проходит алерт

1. Внутренний workflow отправляет алерт через `POST /v1/messages`.
2. Бот вычисляет ключ объекта и состояние инцидента. Новый эпизод имеет новую
   generation; повторное событие не должно создавать новую карточку само по себе.
3. Начальная аудитория и намерения доставки сохраняются до Telegram HTTP.
4. Для каждого получателя ведётся отдельная копия и её состояние доставки.
5. Повторы, SPI, заметки, Mute и Resolved согласовываются с текущими revisions
   и, как правило, редактируют уже известное сообщение.
6. После закрытия следующая firing generation получает новые сообщения.

`ALERT_LEVELS` по умолчанию — `10,20`: меньшее число означает больше полномочий.
Получение требует `receive_level >= level` инцидента; действие эскалации требует
подходящего admin level. Эскалация — явное действие, не автоматический таймер.
Изменение уровня или включение интереса не должно само по себе переигрывать
аудиторию открытых инцидентов.

На закрытой карточке Mute/Escalate не остаются активными. Mute использует
Alertmanager silence и обновляет соответствующие копии карточки.

### Графики и Chart

Графики обрабатываются отдельными durable jobs. Недоступность рендера не должна
блокировать текстовое уведомление: готовое изображение может появиться позднее
через `editMessageMedia` на том же ID. Если готово заранее, возможен `sendPhoto`.
Лимиты Telegram на подпись учитываются отдельно от полного текста; при слишком
длинной подписи возможен переход к полноценному текстовому сообщению.

**Chart** добавляется сверх обычного лимита ссылок и относится к **показанному**
снимку, а не к ещё ожидающему рендеру. Панель, временной диапазон и variables
подтверждаются контрактом рендера и digest. Если достоверных метаданных нет,
ссылка опускается. Ошибка нового рендера не должна подменять ссылку у старой картинки.
Для Resolved запрашивается обновлённый снимок; при успехе картинка и Chart меняются
вместе, при неудаче может остаться предыдущая картинка.

Caller-provided `images` — отдельный механизм: до трёх проверяемых inline PNG/JPEG
с отдельными receipts/retries. Для произвольных входных картинок происхождение
Chart не придумывается. Их нельзя путать с основной сгенерированной фотографией.

Подробнее: [primary-graph-delivery.md](docs/primary-graph-delivery.md) и README.

## Как проходит рассылка

```text
/mailing → VPN / Alerts / LLM / Cluster → текст → предпросмотр → дата / час или Now
```

- Выбирается одна группа на рассылку. `/mailing TEXT` — совместимый shortcut,
  который всё равно требует явного выбора группы.
- Группа, текст, entities и состояние составления хранятся в БД, не в памяти PTB.
- Получатели определяются по **текущему составу выбранной группы при отправке**.
  Для Alerts дополнительно требуется одобрение владельца.
- Старые рассылки, включая отложенные, имеют группу VPN. В LLM никто автоматически
  не добавляется.
- Нативные entities сохраняют скрытые ссылки, стили и корректные UTF-16 offsets.
- История привязана к исходной доставке. Редактирование работает только с
  подтверждёнными исходными `BroadcastCopy`: новые получатели не добавляются,
  при ошибке edit не отправляется замена.

Новые интерактивные рассылки используют состояния `group_choosing` и
`group_scheduled`, чтобы старый VPN-only процесс при rolling update не мог
ошибочно обработать их как VPN-рассылку. Внутренний plaintext
`POST /v1/broadcasts` сохраняет прежний VPN default.

Подробнее: [mailing-groups.md](docs/mailing-groups.md),
[telegram-mailing-formatting.md](docs/telegram-mailing-formatting.md).

## Данные и гарантии доставки

Основные группы моделей в [models.py](src/socrat_bot/models.py):

- `User`, `UserInterest`, `LinkCode` — пользователи, интересы и привязки.
- `Incident`, `CardDelivery`, `TelegramCard`, `AlertOutbox` — эпизоды, желаемое
  состояние, доставленные копии и работа на отправку/обновление.
- `GraphSnapshot`, `GraphJob` — снимки и ограниченные задания рендера.
- `AlertImage`, `ImageDelivery` — дополнительные inline-картинки и их доставка.
- `Broadcast`, `BroadcastCopy` — рассылки и подтверждённые исходные сообщения.
- `Action`, `Audit`, `SudoRequest` — подтверждаемые действия, аудит и sudo-запросы.

Для надёжной доставки карточек используются сохраняемые намерения/outbox,
конечные leases, generation/revision fences и сравнение desired/applied состояния.
После HTTP результат применяется только к актуальному владельцу работы и эпизоду.
Долгие транзакции во время сетевой доставки не должны становиться способом
синхронизации; предпочтительны короткое изменение состояния и последующий HTTP.

**Exactly-once не обещается.** Telegram может принять сообщение, но ответ потеряется
из-за сетевого сбоя. Такая неоднозначность отличается от явного отказа. Также нельзя
считать, что любая рассылка имеет все гарантии alert outbox: у сценариев разные
механизмы claims и восстановления. Статусы, receipts и документация конкретного
пути важнее общего предположения «всё автоматически повторится».

Миграции находятся в `alembic/versions/`, применяются при старте bot/broker.
PostgreSQL advisory lock сериализует параллельный запуск миграций. Для изменения
схемы нужно учитывать одновременно работающие старые и новые процессы.
Переход к интересам выполнен отдельно стадиями expand/contract; небезопасно
просто склеивать такую границу релизов для уже работающей старой установки.

## Интеграции и границы доступа

- **Telegram:** входящие события через webhook, исходящие операции через Bot API.
- **Внутренние workflow / n8n:** сообщения, алерты, ссылки SPI, заметки и события
  действий; бот не является универсальным workflow engine.
- **Grafana и graph gateway:** правила, ссылки, проверенные снимки. Источник gateway
  находится в соседнем проекте; его API-контракт нельзя менять только в боте.
- **Alertmanager:** silence для Mute.
- **Kubernetes API:** ограниченные операции отдельного updater.
- **Sudo:** клиент получает решение broker и затем запускает локальный sudo.
  Это не замена системной политики sudoers и не отмена её ограничений.

В production наружу предназначен только Telegram webhook. Внутренние API не нужно
выставлять публично: они защищаются `X-Internal-Token` и сетевыми границами.
Webhook проверяет `X-Telegram-Bot-Api-Secret-Token`. Конкретные меры для каждого
сервиса нужно смотреть в его коде и инфраструктурной конфигурации, а не выводить
из наличия одного общего токена.

Секреты, API-ключи, токен бота, дампы БД и реальные пользовательские данные нельзя
коммитить. Диагностика не должна включать приватные тексты, callback payloads,
URL с секретами или сырые сетевые исключения. Структурированные stdout-события
могут собираться существующим OTel/Loki pipeline; новый exporter для этого не нужен.

## Разработка и проверки

Работать нужно на отдельной тестовой базе, не на production DB.

```bash
uv sync --locked
uv run pytest -q
uv run qg validate
```

Без `TEST_POSTGRES_URL` PostgreSQL-сценарии пропускаются. Для полного прогона:

```bash
# База должна быть одноразовой: тесты создают и удаляют таблицы.
export TEST_POSTGRES_URL='postgresql+psycopg://postgres@127.0.0.1:55440/socrat_test'
TZ=UTC uv run pytest -q
```

Список проверок Ruff и других операций — в `qg.yaml` и CI. После изменения
декларации Quality Graph запускать `uv run qg generate`, затем `uv run qg validate`;
генерируемые workflow не редактировать вручную.

Перед изменением доставки полезно отдельно проверить: повтор события, гонку
ревизий, истечение lease, opt-out перед отправкой, Resolved, неуспешный HTTP,
повтор callback и сохранение клавиатуры. Для миграций нужны заполненная старая
схема и проверяемый upgrade/downgrade, а не только создание пустой новой БД.

Локальный запуск bot с реальным токеном может зарегистрировать webhook и начать
фоновые циклы. Это не безобидная проверка импорта: использовать тестовый бот
и отдельное окружение. Живые acceptance-тесты выполняются только с разрешённым
получателем, изолированным состоянием и удалением известных тестовых сообщений;
не нужно переигрывать реальные инциденты или массово рассылать проверки.

## Как выпускаются изменения

Штатный путь:

```text
socrat-bot main
  → GitHub CI: lint / tests / build
  → неизменяемый образ в Harbor
  → обновление image tag/digest в homelab
  → автоматическая сверка Argo CD
```

Код приложения находится в этом репозитории; Helm/Kubernetes/GitOps-конфигурация —
в `homelab`. Обычный релиз не требует ручного image patch, Helm upgrade или
принудительного Argo sync. Push в `main` запускает выпуск, поэтому даже изменение
документации не следует считать гарантированно не затрагивающим deployment.

Перед миграцией сохраняется приватная резервная копия. После выпуска проверяются
не только зелёные CI/Argo статусы, но и фактические image digest, завершение rollout,
версия схемы и здоровье сервиса. Для больших схемных изменений нужны совместимые
этапы выпуска; rollback к старому коду без подходящей схемы может быть небезопасен.
